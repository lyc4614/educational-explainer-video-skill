# 从SRT到成片

这是一条分阶段、可定位问题的制作路径。输入是有权使用的稿件、SRT及必要来源；输出是按约定格式验证过的版本化视频。仓库示例用于演示工程机制，不会自动替使用者写分镜、核实教育政策、生成所有图片或制作配音。架构背景见[工程思想与架构](工程思想与架构.md)。

## 先运行示例，再替换内容

在 `examples/layered-explainer/` 目录中运行：

```sh
npm install
npm run dev
```

安装需要可用的Node.js/npm和依赖下载条件。开发命令启动Remotion Studio，便于播放、跳帧和检查图层。查看后可运行：

```sh
npm run render
```

具体脚本、组合名称、输出位置与依赖版本以示例的 `package.json` 和 README 为准。首次运行可能还需要下载渲染浏览器。Studio服务停止后需重新启动；Studio预览和导出的MP4是两种不同产物。这里提供代码驱动预览与渲染，未实现剪映式拖拽剪辑。

开始自己的视频时，复制示例成独立项目，保留演示版本供对照。下面的 `production-brief.json`、`asset-plan.json` 和QA记录由当前项目维护；运行开发或渲染命令不会自动完成这些规划。

## 1. 固定输入与成片合同

登记源文件的SHA-256、文字和时间权威、画幅、帧率、时长、音频方式、已认可参考及其认可范围。原稿与SRT冲突时先确认权威版本，不能边写场景边悄悄修正文案。

检查SRT是否有空字幕、非正时长、顺序倒置或时间重叠。保留文字与起止时间，按统一帧率换算帧边界；不要把逐条取整得到的时长相加后当作全片时长。需要换行时只插入排版换行，不删字、不改时间。

仓库的确定性助手可用于解析时间线和校验制作计划，例如从仓库根目录运行：

```sh
node scripts/build-timeline.mjs inputs/source.srt timeline.json --fps 30
node scripts/validate-brief.mjs production-brief.json --source-root .
```

这些命令假定使用者已准备相应文件。相对来源路径要在声明的 `--source-root` 下解析，并与实际字节哈希一致。具体参数以脚本说明为准。项目运行记录可能包含本地解析路径，公开分享前应另行导出可移植、无私人信息的版本。

没有收到音频时，先明确无声合同或补齐音频输入。无声版不能标成带声成片；后续新增配音也需要重新检查同步与音频流。

## 2. 提取语义，组成视觉段落

对每个完整意思记录原句、字幕ID、时间包络、传达功能、人物/物件、动作、关系和观众应理解的结论。再把这些语义单元组成镜头：一个镜头有一个主要解释动作，可能覆盖多条字幕。

在 `production-brief.json` 中为元素写明 `sourcePhrase` 与 `explanatoryRole`；为镜头写明时间、主次元素、进入/退出状态、`continuityAnchor` 和检查帧。数字、公式、资格或因果没有足够来源时保持待核实，不能靠好看的图表补齐证据。

## 3. 规划素材依赖和空间

先打开 `material-library/index.html` 或读取 `material-library/catalog.json`，按本段语义检索。把计划写入项目的 `asset-plan.json`：

- 每个主体是透明图层 `cutout`，还是自带背景的完整场景 `scene`；决定复用、补图或代码绘制的原因。
- 缺失素材按依赖顺序排队，记录需要沿用的主体或风格参考；没有缺项时队列为空即可。
- 每镜划出标题、主体、数据和字幕区域，明确入场、停靠、数据出现、阅读与退出的帧范围。
- 指定哪些运动中间态需要先检查，哪些卡片、公式或图表稍后叠加。

人物、校园、文具等素材要服务当前解释，不必把素材库全部用上，也不必让同一栋楼贯穿整片。图像生成需要自己的工具或账户；仓库不提供凭据、额度或一键补图接口。素材选择与入库规则见[素材与动效复用](素材与动效复用.md)。

## 4. 先验证透明素材与运动中间态

新透明图使用真实alpha通道，不接受把棋盘格画进图片来表示透明。对实际PNG测量尺寸、SHA-256、透明度和可见边界，并在深、浅背景上检查白边、裁切、残影和多余阴影。

按照可见边界中心放置主体；先制作入场、移动、停靠、让位和退出。预留的数据区此时可以只用布局辅助框，交付前移除。检查最大移动范围、旋转范围、阴影、标签跟随和与字幕区的间距。

中间态可以是几张关键帧，也可以是短视频，不要求每次局部修改都另出完整第二条视频。它的目的，是在数据尚未遮住问题前确认构图与运动成立。PNG仍是静态整体，不能将平移称为行走，将缩放称为转身，或将裁切称为新相机角度。

## 5. 接入数据、轻卡片和公式

先让观众认识主体，再让数据成为焦点。卡片按关系布局：顺序用行列，对应用连接，四项转换可用平衡分组，定量比较使用明确的共同尺度。类别标签和主要数值要有主次，公式成为结论时让出空间。

历史值标签直接显示原值及单位、年份、类别、近似词和来源范围；只动画图形几何。环形明确 `whole`，未报道部分保持中性，不能推断为“失败人数”。独立口径的数据分别展示，未证实可比时不构成排名。折线横轴不等距时要显式映射，不能按数组下标假装等间隔。

复用图表组件时只接入图表主体，去掉演示场景的大背景、标题与页脚。安排同一区域旧卡片与新图表的互斥窗口，标签、连线、阴影跟随同一姿态。详细约束见[图表动效规范](../references/chart-motion.md)。

## 6. 合成独立字幕并检查连续性

字幕按原SRT时间显示在独立安全区，必要时语义换行；同时检查长标签、脚注与来源说明，不能侵入字幕。竖屏需要重新排列主体和关系，不能把横屏整张缩成小图。

逐个查看相邻镜头的最后有意义帧与下一镜首帧：同一物件身份是否保持？停靠位置是否延续？检查是否先发生，结果是否后出现？旧图层是否退出干净？随后连续播放过渡，确认位置和速度没有突变。静止边界帧通过仍不能证明播放节奏自然。

## 样片与审阅范围

制作计划中的A/B/C用于控制样片风险：新主题或未认可视觉系统先做20–30秒完整样片；已认可风格但引入大量新元素或复杂隐喻时做8–12秒微样片或关键帧；同一已认可系列的低风险复用可直接完整制作，但仍需计划和关键帧。应按已有认可的实际范围继续，避免把一次配色认可扩大成任意新主题的认可。

`standard-efficient` 与 `strict-audit` 控制审阅密度，与样片等级相互独立。常规成熟制作可使用前者；正式审计等需要更高证据密度的场景按[生产流程规范](../references/production-workflow.md)选择。两者最终媒体技术要求相同。

## 验收与版本回归

验收针对最后一次修改后的源码与实际导出字节，按顺序完成：

| 范围 | 要验证的内容 |
| --- | --- |
| 行为与契约 | 时间线、brief、类型与组合注册；关键姿态边界、结果不早于来源、数据几何、互斥窗口 |
| 视觉 | 各镜代表状态、入场、最大范围、停靠、数据展开、阅读停留；每个变化边界两侧与接触表 |
| 回归 | 最后一次源码变更后的最终回归；同环境中可对未改画面作图像或哈希比较 |
| 实际播放 | 使用实际导出视频向前播放，检查变化段、过渡和结尾；记录实际播放范围 |
| 媒体 | 版本路径与SHA-256、视频/音频流、编码、尺寸、帧率、帧数、时长容差和完整解码 |

针对真正的行为写测试，例如“停靠结束与数据开始时主体位置一致”“历史标签始终准确”“旧卡片与替代图表不同时可见”。源码文本中出现了某个字段或一张截图看起来正确，不足以证明行为。

示例项目提供的测试和类型检查以其 `package.json` 为准；正式成片另用 `scripts/validate-media.mjs` 对照项目的媒体合同检查，准备可用的FFmpeg与FFprobe。媒体探测成功不能代替完整解码。清除示例占位内容、确认最终字幕与画面属于当前稿件后再交付，详细门槛见[QA与交付规范](../references/qa-and-delivery.md)。

新文件采用版本化名称，保留已认可旧版。失败或未完整解码的文件留在工作目录，不进入交付目录。`production-run.json` 记录当前文件哈希、实际执行的检查、样片认可范围与未做事项；若仅从某个章节开始播放，应如实记录，不能写成全片播放通过。技术验收通过与观众主观认可也分别记录。
